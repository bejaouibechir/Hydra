Prove the connection exists

Prove that the declared source, destination, and transformations are ready while keeping the job free of output writes.

hdrctl testabout 8 minutesmanifests validated

1. Objective

Goal

Use hdrctl test first-job after strict manifest validation. Read each section separately so you know whether source access, destination configuration, transformations, and environment lookup are ready.

Why this matters

A valid schema can still point at an unavailable file, driver, database, or credential. The test command adds connector-aware checks while deliberately stopping before execution, giving you a safe gate to run in a workstation or continuous-integration job.

Course project

Keep working from the cli-course folder. The job is named first-job; every command and terminal excerpt in this lesson was run against that same project.

Prerequisites

  • Lesson 3 completed and its checklist confirmed.
  • The repository clone and hdrctl entry point from lesson 1.
  • A terminal opened in the parent folder that contains first-job.

Evidence rule

Treat the terminal verdict as evidence for this exact command, project state, and machine. Preserve the command beside the result when you record the run. A later execution can report a different duration or process identifier without changing the meaning of a successful state. Do not copy those variable values into an operational threshold. Instead, verify the named files, resolved identifiers, row counters, step states, or HTTP status that the command is designed to prove. If your output differs in one of those facts, stop here and reconcile the project with the preceding lesson before continuing. Before moving on, keep a compact run record with the working directory, the command you typed, the manifests you changed, and the stable facts you confirmed. That record is more useful than a screenshot alone because another reader can reproduce it. Re-open the relevant generated file when the command writes data, and compare its header and content with the declared source, transformation order, destination, or dependency. This habit keeps the cumulative project honest: every new capability is added on top of a state that was observed, explained, and independently checkable rather than merely assumed.
