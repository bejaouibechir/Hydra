Lesson 9 of 11 · Build a workflow

Compose your jobs into a workflow

Wrap the cumulative job in a manual workflow, add a completion action, and validate the manifest and dependency graph before running either step.

hdrctl workflow validateabout 12 minutesproject inventoried

1. Objective

Goal

Create workflow.yaml beside first-job. Declare one job step and one dependent log action, then use hdrctl workflow validate workflow.yaml to prove the model and graph are valid.

Why this matters

A job describes one data movement; a workflow describes ordering across jobs and actions. Validating first catches missing fields, duplicate names, unknown dependencies, and cycles without executing the job, making orchestration changes reviewable before they touch data.

Course project and evidence rule

Continue in cli-course. The job remains first-job, and workflow lessons add workflow.yaml beside it. The terminal excerpts shown here come from that cumulative project. Treat each verdict as evidence for this exact command, project state, and machine. Preserve the command beside the result when recording a run. Durations and process identifiers can vary without changing a successful state; do not turn them into thresholds. Verify instead the named files, resolved identifiers, row counters, step states, or HTTP status the command is designed to prove. Keep the manifest and generated data beside that record so another operator can reproduce the same check from a clean terminal. This small evidence bundle makes configuration drift visible and keeps the next lesson grounded in a known successful state. If one of those facts differs, reconcile the preceding lesson before continuing. Before moving on, keep a compact run record with the working directory, the command you typed, the manifests you changed, and the stable facts you confirmed. That record is more useful than a screenshot alone because another reader can reproduce it. Re-open the relevant generated file when the command writes data, and compare its header and content with the declared source, transformation order, destination, or dependency. This habit keeps the cumulative project honest: every new capability is added on top of a state that was observed, explained, and independently checkable rather than merely assumed.

Prerequisites

  • Lesson 8 completed and checked.

2. Steps

01Declare the workflow identity

Objective

Create the top-level workflow mapping and manual trigger.

Actions

  1. Create workflow.yaml in cli-course.
  2. Set the name to first-job-workflow.
  3. Keep the trigger manual for this guided run.
workflow:
  name: "first-job-workflow"
  description: "Run the guided CSV job, then record completion."
  trigger:
    type: manual
What you should see

The document has the required top-level key, a unique name, and a supported trigger type.

workflow:
  name: "first-job-workflow"
  trigger:
    type: manual

02Add the job step

Objective

Reference the existing cumulative job from the workflow directory.

Actions

  1. Add run_first_job under steps.
  2. Set type to job and job to ./first-job.
  3. Leave depends_on empty.
steps:
  - name: "run_first_job"
    type: job
    job: "./first-job"
    depends_on: []
    on_failure: fail
What you should see

The first step points at a configured job and has no upstream dependency.

- name: "run_first_job"
  type: job
  job: "./first-job"
  depends_on: []

03Add the completion action

Objective

Create a second step that can run only after the job succeeds.

Actions

  1. Add an action step named record_completion.
  2. Use the implemented log action.
  3. Depend on run_first_job.
- name: "record_completion"
  type: action
  action: log
  params:
    message: "first-job-workflow completed successfully."
  depends_on: ["run_first_job"]
  on_failure: fail
What you should see

The dependency forms a simple job-to-action sequence.

run_first_job → record_completion

04Validate the workflow graph

Objective

Check the workflow model and dependency ordering without executing it.

Actions

  1. Run the workflow validator against the new file.
  2. Do not use workflow run until this verdict is clean.
hdrctl workflow validate workflow.yaml
What you should see

The observed validator output is a single successful verdict.

✅ Workflow valid — no errors detected.
