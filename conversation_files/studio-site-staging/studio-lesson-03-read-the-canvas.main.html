Recognize nodes, ports and edges

Create the workflow shell, enter its editor, and learn what Studio's nodes, handles, edges, and scene switcher represent.

Jobs configurationabout 10 minutesAPI online

1. Objective

Goal

Create guided-workflow with a manual trigger and open it in the editor. Distinguish Jobs configuration, where one job is source-to-destination, from Workflow configuration, where saved jobs and actions form a DAG.

Why this matters

The same screen hosts two related graphs. Mixing their meanings leads to invalid designs: connector nodes belong inside jobs, while Job and Action nodes belong in workflow orchestration. Ports and directed edges become YAML references and dependencies.

Course project

Keep one cumulative Studio project named studio-course, one manual workflow named guided-workflow, and one job named first-job. Each lesson builds on the state saved by the previous one.

Prerequisites

  • Hydra API started with hdrctl serve.
  • Studio started from Hydra/studio with npm run dev.
  • The preceding lesson completed before continuing.

03Read nodes and edges

Objective

Interpret the toolbar counter as graph structure, not run output.

Actions

  1. Locate the monospace counter beside the workflow name.
  2. Read nodes as graph items and edges as directed connections.
  3. Do not interpret either count as data rows.

04Read direction and ports

Objective

Understand what a connection will mean before drawing one.

Actions

  1. Switch between the two scene tabs.
  2. Notice that Sources have no input capacity and Destinations have no output capacity.
  3. Follow every edge from source handle to target handle.
Jobs configuration ↔ Workflow configuration
What you should see

Job scenes model source → transformations → destination; workflow scenes model dependencies among jobs and actions.

Job: source → transformations → destination
Workflow: jobs/actions → depends_on
Evidence rule

Record the visible label, selected scene, saved file, and stable state that each gesture proves. Counts tied to your workspace and run durations can change, so do not use them as fixed thresholds. When Studio writes YAML, compare the generated key with the field you edited; when it runs work, compare the node state with the Runs detail. This keeps the canvas, the DSL, and the engine tied to the same observable project instead of treating a green screen as sufficient evidence. Before continuing, reopen the saved node or panel and reproduce the observation from a neutral selection. Keep the project path, workflow name, job tab, active scene, and relevant field beside your note so another operator can repeat the same check. If a file is generated, inspect it on disk as well as in Studio. If a run is involved, wait for a terminal state and use the Runs page instead of relying on a transient animation. These habits reveal autosave, workspace, and scene mistakes early, while the project is still small enough to correct without obscuring the cause.
