Lesson 12 of 12 · Handle failure

Wrap a step in retry and error scopes

Use Studio's visual policy containers without serializing the containers themselves, and verify the inherited retry and on_failure fields on their direct children.

Containersabout 12 minutestwo-job workflow composed

1. Objective

Goal

Place a Retry Scope and an Error Scope on the workflow canvas. Move first-job directly into Retry Scope and second-job directly into Error Scope, then inspect the generated step policies.

Why this matters

Containers are visual grouping nodes, not executable workflow steps. The workflow serializer excludes them and copies a Retry Scope policy to direct children, or an Error Scope on_failure policy to direct children. Direct parentage matters; policy inheritance is not inferred from visual proximity.

Course project

Continue with studio-course, the manual guided-workflow, and the first-job canvas saved by the preceding lesson. Do not create a parallel replacement project.

Prerequisites

  • The top bar shows API online.
  • The cumulative workflow is open in the editor.
  • The preceding lesson checklist is complete.

02Apply Retry Scope

Objective

Give first-job the retry policy stored on its direct parent container.

Actions

  1. Drag Retry Scope onto empty canvas space.
  2. Drag first-job into the scope until it becomes a child.
  3. Keep the default scope values created by WorkflowEditor for this exercise.
Retry Scope ← first-job
What you should see

The implemented default retry scope carries max three and delay five for its child.

Retry Scope
retry:
  max: 3
  delay: 5

03Apply Error Scope

Objective

Give second-job the on-failure policy of a separate direct parent.

Actions

  1. Drag Error Scope onto empty space.
  2. Move second-job directly inside it.
  3. Choose the scope's on-failure policy in its configuration.
Error Scope ← second-job → on_failure: skip
What you should see

The Error Scope policy is copied to the direct child when the workflow is serialized.

Error Scope
on_failure: skip

04Verify executable YAML

Objective

Prove containers disappear while child policies remain on workflow steps.

Actions

  1. Open Hydra DSL.
  2. Confirm there is no container step.
  3. Find retry on first-job and on_failure on second-job, then save.
Hydra DSL → workflow.yaml → Save
What you should see

The serializer excludes visual containers and emits only executable job steps with inherited policies.

- name: first-job
  type: job
  retry:
    max: 3
    delay: 5
- name: second-job
  type: job
  on_failure: skip
Saved ✓
Evidence rule

Record the active scene, visible label, saved file, and stable state that each gesture proves. Workspace counts and run durations can change, so do not turn them into fixed thresholds. When Studio writes YAML, compare the generated key with the field you edited; when it runs work, compare the node state with the Runs detail. This evidence bundle keeps the canvas, the DSL, and the engine tied to the same observable project instead of treating a green badge or animation as sufficient proof. Before continuing, reopen the saved node or panel and reproduce the observation from a neutral selection. Keep the project path, workflow name, job tab, active scene, and relevant field beside your note so another operator can repeat the same check. If a file is generated, inspect it on disk as well as in Studio. If a run is involved, wait for a terminal state and use the Runs page instead of relying on a transient animation. These habits reveal autosave, workspace, and scene mistakes early, while the project is still small enough to correct without obscuring the cause.
