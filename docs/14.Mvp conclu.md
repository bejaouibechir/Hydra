L'Étape 8 du MVP Hydra (Connecteurs Base de Données) est **validée avec succès**. Le framework supporte désormais l'extraction et le chargement depuis/vers MySQL et MariaDB via une architecture générique extensible. Trois scénarios d'intégration ont été testés et validés en environnement Docker.

## 📈 Progrès Réalisés

### **Architecture Implémentée**

**Connecteur MySQL/MariaDB unifié** :

- Héritage d'une classe de base `BaseDBConnector` pour mutualiser la logique commune
- Support streaming par batches (connexion maintenue, curseur itératif)
- Gestion des modes `append` et `replace`
- Résolution automatique des credentials via variables d'environnement

**Registry Générique** :

- Dispatch dynamique : `{"csv": CSVConnector, "mysql": MySQLMariaDBConnector, "mariadb": MySQLMariaDBConnector}`
- Factory pattern : `build_connector(name, config)` → instanciation automatique selon type
- Extensibilité : Ajout de nouveaux connecteurs sans modification du core

**Executor Multi-Connecteurs** :

- Détection automatique du type source/destination
- Configuration adaptative selon le connecteur (job_dir pour CSV, connection pour DB)
- Pipeline bout-en-bout : Extract (DB/CSV) → Transform (Pandas) → Load (DB/CSV)

## 🔧 Problèmes Résolus

### **1. Résolution Chemins Relatifs (Critique)**

**Symptôme** : Fichiers CSV créés à la racine du projet au lieu du dossier job.

**Cause Racine** : Le registry ne passait pas le paramètre `job_dir` au CSV Connector.

**Solution** :

```python
# Registry adapté selon le type de connecteur
if ctype == "csv":
    job_dir = config.get("job_dir")
    return CSVConnector(name, config, job_dir)  # Signature spécifique CSV
else:
    return DBConnector(name, config)  # Signature standard DB
```

**Impact** : Chemins relatifs (`./data/file.csv`) résolus correctement depuis le dossier du job.

---

### **2. Limitations Pandas eval()**

**Symptôme** : Expressions conditionnelles ternaires refusées (`'Senior' if age >= 30 else 'Junior'`).

**Cause** : `DataFrame.eval()` utilise un sous-ensemble Python limité (pas de support `IfExp` AST node).

**Solution MVP** : Simplification des transformations pour Test 9.

**Workaround Temporaire** :

```yaml
# Au lieu de conditions complexes
steps:
  - select:
      columns: [id, full_name, email, age]
# Transformation conditionnelle reportée post-MVP
```

---

### **3. Types CSV (String par Défaut)**

**Symptôme** : Comparaisons numériques échouent (`age > 0` avec age="29" string).

**Cause** : CSV Connector lit toutes valeurs en string (comportement standard Python csv module).

**Solution** : Opération `cast` explicite avant filtrage.

```yaml
steps:
  - cast:
      mapping:
        age: int
  - filter:
      expr: age > 0
```

---

### **4. Manifests YAML (Bugs Génération)**

**Symptôme** : Script BAT de génération produisait `path:` au lieu de `table:`, `source:` au lieu de `from:`.

**Solution** : Correction manuelle des 3 manifests (mysql_to_csv, csv_to_mysql, mysql_to_mysql).

**Apprentissage** : Les scripts de génération nécessitent une validation rigoureuse avant utilisation.

## 🚧 Fonctionnalités Reportées (Post-MVP)

### **1. Mode Upsert (Haute Priorité)**

**Besoin** : Gestion des conflits de clés primaires lors de l'insertion.

**Comportement Actuel** :

- `append` : Erreur si clé existe (`IntegrityError: Duplicate entry`)
- `replace` : Écrase toute la table (perte données existantes)

**Comportement Souhaité** :

```yaml
destinations:
  mysql_target:
    load:
      table: employees
      mode: upsert           # ← Nouveau mode
      key: [id]              # ← Colonne(s) de clé
```

**Implémentation Future** :

```sql
-- MySQL
INSERT INTO employees (id, name, email) 
VALUES (1, 'Alice', 'alice@corp.tld')
ON DUPLICATE KEY UPDATE name=VALUES(name), email=VALUES(email)

-- PostgreSQL
INSERT INTO employees (id, name, email) 
VALUES (1, 'Alice', 'alice@corp.tld')
ON CONFLICT (id) DO UPDATE SET name=EXCLUDED.name, email=EXCLUDED.email
```

**Effort Estimé** : 1-2 jours (support MySQL/MariaDB/PostgreSQL).

---

### **2. Détection AUTO_INCREMENT (Moyenne Priorité)**

**Besoin** : Exclure automatiquement les colonnes auto-générées lors de l'insertion.

**Comportement Actuel** : L'utilisateur doit exclure manuellement `id` dans les transformations.

```yaml
steps:
  - select:
      columns: [name, email, age]  # ❌ Exclusion manuelle de 'id'
```

**Comportement Souhaité** :

```yaml
destinations:
  mysql_target:
    load:
      table: employees
      auto_increment: [id]   # ← Exclusion automatique
```

**Implémentation Future** : Introspection `INFORMATION_SCHEMA.COLUMNS` pour détecter `EXTRA LIKE '%auto_increment%'`.

**Effort Estimé** : 1 jour (requête SQL + logique exclusion).

---

### **3. Opération `case_when` (Basse Priorité)**

**Besoin** : Conditions multiples pour calculs complexes.

**Limitation Actuelle** : Pandas `eval()` ne supporte pas les ternaires Python.

**Opération Proposée** :

```yaml
steps:
  - case_when:
      column: risk_level
      conditions:
        - when: score >= 80
          then: High
        - when: score >= 50
          then: Medium
        - otherwise: Low
```

**Implémentation Future** : Utiliser `np.select()` ou `pd.Series.map()` au lieu de `eval()`.

**Effort Estimé** : 2-3 jours (nouveau modèle Pydantic + logique Pandas).

---

### **4. Support Expressions Python Natives (Basse Priorité)**

**Limitation** : `calculate` utilise `DataFrame.eval()` qui limite les opérateurs disponibles.

**Alternatives Envisagées** :

- **Option A** : Parser AST Python et convertir en opérations Pandas natives
- **Option B** : Utiliser `apply()` avec `eval()` Python natif (moins performant)
- **Option C** : DSL personnalisé avec syntaxe simplifiée

**Décision** : Reporter en v2.0 après retours utilisateurs sur cas d'usage réels.

## 🏆 Conclusion

L'Étape 8 valide la **viabilité architecturale** du framework Hydra pour des cas d'usage réels d'intégration de données. L'approche registry + interfaces permet une **extensibilité sans friction** : ajouter un nouveau connecteur (PostgreSQL, MongoDB, API REST) nécessite uniquement d'implémenter l'interface `Connector` et d'enregistrer le type dans le registry.

Les limitations identifiées (upsert, auto-increment, transformations complexes) sont **acceptables pour un MVP** et constituent une roadmap claire pour les versions suivantes. Le framework est **prêt pour des tests utilisateurs** et l'intégration de cas d'usage métier réels.
