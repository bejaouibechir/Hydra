# Partie I Architecture

## 1. Composants principaux de l’ETL (vue fonctionnelle)

### 1.1. Couche publique : `etl/`

- **`etl.engine`**
  
  - Point d’entrée “officiel” du moteur.
  
  - Expose une API stable : `run_job(config_path)`, `run_pipeline(source, dest, transform)`, etc.
  
  - Ne connaît pas les détails internes (connecteurs, DuckDB, etc.).

- **`etl.types`**
  
  - Types “publics” : `Job`, `JobStatus`, `JobResult`, `JobError`, etc.
  
  - Utilisés par la CLI aujourd’hui, par une API REST ou un SDK demain.

---

### 1.2. Couche interne exécution : `internal/runner/`

- **`executor`**
  
  - Lit la config parsée.
  
  - Construit un **plan d’exécution séquentiel** (liste d’étapes).
  
  - Pilote Extract → Transform → Load en batch.
  
  - Applique les règles d’erreur (`fail_fast`, `skip_row`, `retry`).

- **`context`**
  
  - Contexte d’exécution :
    
    - `job_id`, timestamps, compteur de lignes, stats, paramètres runtime (dates, filtres).
  
  - Mis à jour à chaque étape ; accessible aux loggers.

---

### 1.3. Parsing & validation : `internal/parser/`

- **`source.py`**
  
  - Charge `source.yaml` / bloc `sources:`.
  
  - Valide : type (`mysql`, `csv`…), options, schéma.

- **`destination.py`**
  
  - Charge `destination.yaml` / bloc `destinations:`.
  
  - Valide : table cible, mode (`insert`, `upsert`, `truncate_then_load`…).

- **`transform.py`**
  
  - Charge `transform.yaml`.
  
  - Produit un **AST de transformation** : liste ordonnée de steps (`filter`, `join`, `calculate`, `aggregate`, `clean`…).
  
  - Vérifie cohérence : colonnes existantes, types compatibles.

---

### 1.4. Connecteurs : `internal/connector/`

- **`interface.py`**
  
  - Définit les interfaces :
    
    - `connect()`, `test_connection()`
    
    - `read_batches(query/spec)`
    
    - `write_batches(rows, mode)`
  
  - Contrat commun pour toutes les sources/destinations.

- **`mysql.py` / `mariadb.py`**
  
  - Implémentent le connecteur relationnel via SQLAlchemy ou driver natif.
  
  - Gèrent transactions par batch, erreurs SQL, timeouts.

- **`csv.py`, `json.py`**
  
  - Lecteurs/écrivains de fichiers (streams ou chunking).

*(Plus tard : `xml.py`, `parquet.py`, `proto.py`, etc.)*

---

### 1.5. Moteurs de transformation : `internal/transform/`

- **`pandas_engine.py`**
  
  - Transformations **ligne à ligne** ou simples :
    
    - cast, rename, calcul de colonnes, nettoyage regex, filtres.
  
  - Travail sur DataFrame en mémoire, sur des chunks raisonnables.

- **`duckdb_engine.py`**
  
  - Transformations **ensemblistes** : joins, agrégations, group by, fenêtres.
  
  - Monte les données (ou références) dans DuckDB et exécute du SQL généré à partir du DSL.
  
  - Évite de réécrire un optimiseur.

- **`jit_compiler.py`** (mode JIT par défaut)
  
  - Optionnel : compile certaines transformations “hot” en code accéléré (Cython/Numba/mypyc).
  
  - L’API reste la même ; c’est un “turbo” interne.

- **`compiled_artifact_runner.py`** (mode artefact activé volontairement)
  
  - Exécute un module compilé (Python compilé ou binaire Go) généré à partir du DSL.
  
  - Activé seulement si l’utilisateur choisit le mode artefact.

---

### 1.6. Cache & back-pressure : `internal/cache/`

- **`memory.py`**
  
  - Tampon de lignes en RAM (file de messages interne).
  
  - Taille max configurable (ex : N lignes ou N Mo).

- **`backpressure.py`**
  
  - Surveille le cache :
    
    - si seuil > 80% → ralentit ou bloque l’extraction.
    
    - si seuil > 100% → lève une erreur claire “destination trop lente”.

- **(optionnel) `disk_cache.py`**
  
  - Tampon disque pour déverser quand RAM saturée (mode dégradé).

---

### 1.7. Logs & métriques : `internal/logger/`

- **`structured.py`**
  
  - Log JSON structuré :
    
    - `{timestamp, level, job_id, step, event, details}`.
  
  - Utilisé partout (parser, executor, connectors, transform).

- **`metrics.py`**
  
  - Compte lignes lues/écrites, durée par étape, erreurs.
  
  - Expose un petit snapshot final dans `JobResult`.

---

### 1.8. Config & secrets : `internal/config/`

- **`loader.py`**
  
  - Charge `etl-config.yaml` + fichiers `source.yaml`/`destination.yaml`/`transform.yaml`.
  
  - Fusionne paramètres globaux + overrides.

- **`secrets.py`**
  
  - Résout les placeholders comme `${SECRETS.DB_PASSWORD}` depuis :
    
    - variables d’environnement,
    
    - `.env`,
    
    - store externe (plus tard : Vault, etc.).

---

### 1.9. CLI : `cli/main.py`

- Composant minimal :
  
  - `etl run --config etl-config.yaml`
  
  - `etl test-connection --source sales_db`
  
  - `etl dry-run --config etl-config.yaml`

---

│   └── main.py                   # Commande « etl run », « etl test-connection », etc.
│
├── examples/                     # Exemples complets de configurations
│   ├── etl-config.yaml           # Exemple pipeline global
│   ├── source.yaml               # Source d'exemple (DB, CSV…)

## 3. Dépendances du projet

**Runtime :**

- Python **3.11+**

- (Plus tard) Go toolchain si tu génères des artefacts Go.

**Libs Python principales :**

- **YAML & validation**
  
  - `pyyaml` (ou `ruamel.yaml`)
  
  - `pydantic` (ou `pydantic-core`) pour valider les configs/AST.

- **Base de données**
  
  - `sqlalchemy` + driver MySQL/MariaDB (`mysqlclient` ou `pymysql`).

- **Transformations**
  
  - `duckdb` (obligatoire pour joins/aggregations).
  
  - `pandas` (optionnel mais pratique pour transformations ligne à ligne).

- **Accélération (JIT/compilé)**
  
  - `Cython` *ou* `numba` *ou* `mypyc` (à choisir plus tard).

- **CLI / ergonomie**
  
  - `typer` ou `click`.

- **Logs**
  
  - standard `logging` ou `loguru` (mais format JSON structuré maison).

- **Tests**
  
  - `pytest`.

## 4. Approche pour intégrer Go plus tard

Idée clé : **la partie publique reste Python, mais la logique lourde peut passer en Go progressivement**.

- **Étape 1 : définir une API interne claire**
  
  - `EngineAPI` dans `etl.engine` qui ne dépend PAS de l’implémentation.
  
  - Aujourd’hui : implémentée en Python via `internal/*`.
  
  - Demain : une autre implémentation (service Go) peut prendre le relais.

- **Étape 2 : isolation des parties “heavy”**
  
  - Les fonctions les plus gourmandes (gros joins, agrégations, batch load) sont isolées derrière des interfaces claires (ex : `TransformBackend`, `LoadBackend`).
  
  - Tu pourras les remplacer par :
    
    - un module Go appelé via gRPC,
    
    - ou un binaire Go que Python pilote.

- **Étape 3 : interop**
  
  - Soit via gRPC/HTTP (service Go séparé),
  
  - soit via `subprocess` (binaire Go appelé avec un contrat clair : fichiers d’entrée / sortie).

- **Étape 4 : migration progressive**
  
  - Tu peux commencer par :
    
    - `duckdb_engine.py` → réécriture en Go si besoin.
  
  - Sans toucher aux YAML ni à `etl.engine`.

---

## 5. Approche pour intégrer des extensions (plugins)

Deux grandes familles d’extensions :

1. **Connecteurs supplémentaires**
   
   - Interface : `Connector` dans `internal/connector/interface.py`.
   
   - Un plugin externe implémente cette interface (`class S3Connector(Connector): ...`).
   
   - Déclaration dans la config :
     
     ```yaml
     sources:
      - name: s3_data
        type: "s3_custom"
        plugin: "mycompany.etl_s3_plugin"
     ```

2. **Transformations custom**
   
   - Interface : `TransformationStep` / `CustomTransform` dans `internal/transform`.
   
   - Le DSL permet une step du type :
     
     ```yaml
     steps:
      - custom:
          name: "my_custom_step"
          plugin: "mycompany.etl_custom_transforms"
          params:
            foo: bar
     ```

**Découverte des plugins :**

- Soit via un système simple (“plugins/” dans PYTHONPATH),

- soit via entry points (`setup.cfg` / `pyproject.toml`).

## 6. Gestion des anomalies & lacunes (erreurs, flux, cohérence)

### 6.1. Erreurs de transformation / données

- Au niveau DSL, tu prévois un bloc global, par exemple :

```yaml
error_policy:
  mode: "fail_fast"   # ou "skip_row", "continue"
  retry:
    enabled: true
    max_attempts: 3
    backoff_seconds: 2
```

- **`fail_fast`** : première erreur → abort job, rollback batch.

- **`skip_row`** : log détaillé (ligne, cause) → continuer.

- **`continue`** : pour erreurs non critiques (par ex. valeur nettoyée en NULL).

### 6.2. Transactions & DB (MySQL/MariaDB)

- Chargement par **batch** (ex : 5k lignes) :
  
  - `BEGIN`
  
  - `INSERT ...` / `UPSERT ...`
  
  - si erreur : `ROLLBACK` + appliquer `error_policy` (stop ou passer au batch suivant).
  
  - sinon : `COMMIT`.

- Modes possibles dans config destination :

```yaml
load_mode:
  type: "upsert"       # insert|upsert|truncate_then_load
  batch_size: 5000
  transaction: "per_batch"  # ou "per_job"
```

### 6.3. Back-pressure & cache

- Cache mémoire a deux seuils :
  
  - `high_watermark` (ex : 80%) → l’extracteur se met en pause.
  
  - `critical_watermark` (100%) → erreur claire : “destination trop lente / cache plein”.

- Ces événements sont loggés :

```json
{
  "level": "WARN",
  "event": "BACKPRESSURE_ACTIVATED",
  "job_id": "...",
  "cache_usage": 0.83
}
```

### 6.4. Ordre d’exécution & “mini-DAG”

- Le fichier `transform.yaml` définit une **liste ordonnée** de steps → séquence déterministe.

- Pour multi-sources, chaque `join` ou `lookup` mentionne explicitement la source :

```yaml
steps:
  - from: "sales_db.orders"
  - join:
      with: "sales_db.customers"
      on: "customer_id"
```

→ Pas de DAG compliqué pour MVP, mais l’ordre est explicite et reproductible.

### 6.5. Idempotence (relancer un job sans doublons)

Quelques modes possibles (config destination) :

- `natural_key` : on fait de l’UPSERT sur une clé naturelle (ex: `(order_id)`), pas d’inserts en double.

- `staging_table` : chargement dans une table de staging + `MERGE` SQL derrière.

- `job_run_id` : chaque run tague ses lignes ; on peut nettoyer/rejouer si besoin.

---

### 6.6. Artefacts compilés (optionnels)

- Par défaut : **mode interprété JIT** (Python + DuckDB + JIT local).

- Si l’utilisateur le demande :
  
  - le DSL est transformé en code (Python optimisé ou Go),
  
  - compilé en module, stocké dans `artifacts/jobs/job_<id>.bin` ou équivalent,
  
  - et `compiled_artifact_runner.py` exécute ce module.

- Le job garde une trace :
  
  - `config_version`, `dsl_version`, `artifact_version` → traçabilité.
