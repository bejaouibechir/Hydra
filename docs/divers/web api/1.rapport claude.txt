## 🎯 OBJECTIF DU SPRINT

Implémenter un **Web API Connector** pour Hydra permettant l'extraction de données depuis des APIs REST, en respectant les **3 défis fondamentaux** du projet.

---

## 📊 RAPPEL DES 3 DÉFIS HYDRA

### **Défi 1 : Ne pas polluer le cœur du DSL**
- Le DSL central (`pipeline.yaml`, `transformations.yaml`) doit rester simple et stable
- La complexité spécifique aux APIs va dans `sources.yaml`
- Les détails d'implémentation (retry, rate limiting) restent **invisibles** dans le DSL

### **Défi 2 : Décrire explicitement la structure source ET cible**
- Contrairement aux CSV/SGBD, les APIs REST ont des structures variables
- Le `schema` doit mapper explicitement : JSON source → colonnes destination
- Gestion des cas complexes : nested, arrays, recursivité, types mixtes

### **Défi 3 : Pandas/DuckDB suffisent-ils pour les transformations ?**
- **OUI**, si le Web API Connector normalise correctement en amont
- JSON complexe → Records plats (responsabilité du connector)
- Pandas/DuckDB appliquent ensuite les transformations classiques

---

## 💡 DÉCISIONS STRATÉGIQUES PROPOSÉES

### **Décision 1 : Approche Test-Driven Design (TDD)**

**Proposition** : Écrire les tests **AVANT** le code pour garantir la robustesse.

**Justification** :
- ✅ Couvrir les cas **fréquents ET atypiques** identifiés
- ✅ Garantir que le connector gère tous les cas réels
- ✅ Prévenir les régressions futures
- ✅ Documentation vivante des capacités du connector

**Cas réels à tester** :

1. **Nested simple (2-3 niveaux)**
```json
{
  "user": {
    "id": 12345,
    "address": {
      "city": "Tunis",
      "coordinates": [36.8065, 10.1815]
    }
  }
}
```

2. **Arrays d'objets avec nested recursif** (⭐ **très fréquent**)
```json
{
  "postId": 7842,
  "comments": [
    {
      "id": 1,
      "author": "Sami",
      "replies": [
        {
          "id": 2,
          "author": "Leila",
          "parent": {"id": 1, "author": "Sami"}
        }
      ]
    }
  ]
}
```

3. **Hierarchies parent-child** (⭐ **très fréquent**)
```json
{
  "categories": [
    {
      "id": 1,
      "name": "Électronique",
      "children": [
        {
          "id": 11,
          "name": "Smartphones",
          "parent": {"id": 1, "name": "Électronique"}
        }
      ]
    }
  ]
}
```

4. **Arrays de primitives** (⭐ **simple mais délicat**)
```json
{
  "prices": [19.99, 29.90, 5.00, 149.00],
  "features": [true, false, true],
  "tags": ["urgent", "nouveau", "promo"]
}
```

5. **Arrays mixtes (primitives + objets)**
```json
{
  "hobbies": ["reading", "hiking", {"extreme": "skydiving"}]
}
```

**Question au consortium** : Validez-vous cette approche TDD ? Y a-t-il d'autres cas critiques à ajouter ?

### **Décision 2 : Résilience Network (Retry Logic)**

**Proposition** : Implémenter retry automatique avec exponential backoff **dans le connector** (pas exposé au DSL).

**Justification** :
- ✅ Réalité terrain : APIs retournent 429 (rate limit), 503 (server down), timeouts
- ✅ Respecte le Défi 1 : pas de pollution DSL
- ✅ Comportement robuste par défaut

**Implémentation proposée** (invisible pour l'utilisateur) :
```python
# Hardcodé dans le connector
DEFAULT_MAX_RETRIES = 3
DEFAULT_BACKOFF_FACTOR = 2  # 1s, 2s, 4s, 8s
DEFAULT_TIMEOUT = 30
RETRY_ON_STATUS = [429, 503, 504]
```

**DSL reste simple** :
```yaml
sources:
  api_source:
    type: web_api
    connection:
      base_url: "https://api.example.com"
    extract:
      endpoint: "/users"
```

**Question au consortium** : 
- 3 retries max vous semble suffisant ou faut-il augmenter (5) ?
- Faut-il exposer ces paramètres dans le DSL ou les garder internes ?

## 🚨 RISQUES ET ALERTES

### **Alerte 1 : Pollution DSL détectée et corrigée**

**Problème initial** : L'assistant technique a proposé d'ajouter dans le DSL :
```yaml
# ❌ POLLUTION DSL - REJETÉ
sources:
  api_source:
    connection:
      retry:                    # ← POLLUTION !
        max_attempts: 3
        backoff_strategy: exponential
      rate_limit:
        requests_per_second: 10
```

**Correction** : Ces détails sont désormais **internes au connector**, invisibles dans le DSL.

**Action** : Le développeur principal a rappelé fermement les 3 défis. Situation corrigée.

### **Alerte 3 : Gestion des Arrays - Stratégie à valider**

**3 stratégies possibles** :

**Option A : Explode (long format)** - Recommandé
```python
# Input
{"id": 1, "prices": [10, 20, 30]}

# Output
[
  {"id": 1, "price": 10, "price_index": 0},
  {"id": 1, "price": 20, "price_index": 1},
  {"id": 1, "price": 30, "price_index": 2}
]
```

**Option B : Flatten (wide format)**
```python
{"id": 1, "prices_0": 10, "prices_1": 20, "prices_2": 30}
```

**Option C : Keep JSON**
```python
{"id": 1, "prices": "[10, 20, 30]"}
```

**Question au consortium** : 
- Quelle stratégie par défaut pour les arrays de primitives ?
- Quelle stratégie pour les arrays d'objets ?
- Faut-il permettre de choisir dans le schema ?
