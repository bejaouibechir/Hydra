---

## 1) Décision clé : le connecteur Web API doit être “policy-driven”

L’idée Hooks + ErrorHandlers + “Policy layer” est la bonne. Pour le Web API, c’est encore plus important : tu ne veux pas mettre du retry/backoff/circuit-breaker “en dur” dans le connecteur.

Ce que je figerais comme “policies” minimales (MVP) :

* **RetryPolicy** : retries sur erreurs transitoires (429, 502, 503, timeouts), avec backoff + jitter
* **RateLimitPolicy** : respect de Retry-After, plafonds internes (ex: max req/s)
* **CircuitBreakerPolicy** : ouvrir après N échecs, demi-ouverture, fermeture après succès
* **TimeoutPolicy** : connect/read timeouts distincts
* **AuthPolicy** : stratégie interchangeable (API key, Bearer token, OAuth2 client credentials…)

Objectif : le connecteur fait “HTTP + pagination + parsing”, les policies font “résilience/comportement”.

---

## 2) Authentification : prévoir 3 cas “réels” dès J1

Sans sur-implémenter OAuth complet, tu peux cadrer proprement :

* **API Key** (header ou query param)
* **Bearer Token statique** (token fourni via secrets)
* **OAuth2 Client Credentials** (token endpoint + cache en mémoire + refresh avant expiration)

Point important : l’OAuth2 doit être **un plugin/handler** (ou au minimum une classe séparée), pas mélangé au cœur du connecteur. 

---

## 3) Extraction : pagination, incremental, idempotence (les 3 mines)

Avant de coder, je te conseille de choisir une convention claire :

### Pagination

Supporter au moins 2 styles :

* page/per_page (ou limit/offset)
* next link (Link header ou champ next dans JSON)

### Incremental

Décider comment Hydra garde l’état :

* state_file (déjà dans ton DSL) : stocker last_cursor / last_timestamp / last_id
* stratégie “cursor” vs “timestamp” (les APIs varient)

### Idempotence

Si tu fais des appels “write” via API plus tard, il faudra une clé d’idempotence.
Même si ce n’est pas dans le scope immédiat, réserve le champ (ex: idempotency_key_header) pour éviter de casser plus tard.

---

## 4) TDD : ce que je figerais comme matrice de tests

Le Web API connector doit être testé sans Internet.

Je ferais 4 familles de tests, dans cet ordre :

1. **Unit tests parsing/config**

* validation Pydantic
* substitution secrets/config
* erreurs explicites si config incomplète

2. **Unit tests HTTP sans réseau**

* mock du client HTTP (responses / httpx mock / requests mock)
* scénarios : 200, 401, 403, 404, 429, 5xx, timeout
* vérification : RetryPolicy déclenchée uniquement sur transitoire

3. **Tests pagination**

* cas “page/per_page”
* cas “next token”
* vérification : pas de doublons, arrêt correct, respect batch_size

4. **Contract tests “shape”**

* vérifier json_path (ex: data[*])
* mapping colonnes (flatten minimal)
* erreurs si la structure change (option “strict_schema”)

---

## 5) Point que je rajoute (important) : “versioning DSL vs plugins”

Tu as déjà identifié le risque : un plugin peut casser si la grammaire évolue. 
Solution simple (sans complexité) :

* chaque plugin expose : **supported_dsl_versions = ["1.1"]**
* au chargement, Hydra refuse (ou warn) si incompatibilité

C’est léger, mais ça évite les surprises en prod.

---

## 6) Ce que je te conseille de NE PAS faire maintenant (pour éviter l’over-engineering)

* Supporter 15 méthodes d’auth dès le départ (OAuth PKCE, JWT assertion, etc.)
* Gérer GraphQL + REST + SOAP dans le même connecteur
* Implémenter un “schema inference” complexe : reste sur un flatten simple + schema optionnel fourni

---

## 7) Mini-checklist “GO implémentation Web API” (si tu veux verrouiller)

Avant de coder, assure-toi d’avoir :

* Une config claire : base_url, endpoint, method, headers, params, auth, pagination, json_path, incremental, timeouts
* Un découpage net : HTTP client / policies / pagination / parser JSON
* 10 tests “rouges” écrits à l’avance (au moins 1 par scénario critique)

---

Si tu veux mon avis “priorité absolue” : **commence par écrire les tests de pagination + retry/429**, parce que c’est là que 80% des bugs “invisibles” apparaissent en prod (doublons, boucles infinies, throttling mal géré).

Si un utilisateur a vraiment besoin de plus de contrôle, il pourra le faire plus tard via un hook ou un connector custom (Phase 2 extensibilité).

### 4. Stratégie par défaut pour les arrays
**Recommandation claire : Option A "Explode" (long format) par défaut.**  
Raisons :
- C’est le format le plus naturel pour Pandas/DuckDB ensuite (une ligne = un enregistrement atomique).
- Les jointures, agrégations, filtres deviennent triviales.
- Les arrays de primitives deviennent exploitables (ex: avg(price), count(tags)).

**Pour les arrays d’objets complexes/recursifs :**
- Explode récursivement jusqu’à un niveau max configurable (défaut 3, pour éviter l’explosion infinie sur références circulaires).
- Ajouter un champ `_parent_id` ou `_array_index` pour garder la trace de la hiérarchie.

**Option dans le schema :** oui, mais minimale.
```yaml
schema:
  fields:
    - name: comment_text
      path: "comments[*].text"
      array_handling: explode  # ou flatten / keep_json (défaut: explode)
```

Trois choix seulement : `explode` (recommandé), `flatten` (wide, colonnes prices_0, prices_1…), `keep_json` (string JSON).  
Pas plus, sinon on pollue.

### 5. Headers personnalisés nécessaires Sprint 1 ?
**Oui, absolument.**  
C’est le compromis parfait pour supporter les API keys simples sans implémenter tout le système d’auth.

Proposition DSL minimale :
```yaml
sources:
  api_github:
    type: web_api
    connection:
      base_url: "https://api.github.com"
      headers:                  # ← ajouté ici
        Authorization: "token ${SECRET:GITHUB_TOKEN}"
        User-Agent: "Hydra/1.0"
        Accept: "application/vnd.github.v3+json"
    extract:
      endpoint: "/repos/octocat/Hello-World/issues"
```

### 6. Méthodes HTTP autres que GET dès le Sprint 1 ?
**Non.**  
GET seulement pour le MVP.  
Les cas POST/PUT avec body complexe sont rares pour de l’extraction pure.  
Si besoin urgent, l’utilisateur peut attendre Sprint 3 ou écrire un connector custom.

### 7. Auto-détection du schema ?
**Sprint 2+.**  
Priorité moyenne.  
Manuel d’abord → fiabilité maximale + apprentissage utilisateur.  
Auto ensuite (analyse des 50-100 premiers records) comme mode `mode: auto` optionnel.

### 8. Gestion des erreurs métier (200 avec {success:false})
**Edge case → Sprint 2.**  
On peut ajouter un champ optionnel dans le schema plus tard :

Mais pas bloquant pour MVP.
