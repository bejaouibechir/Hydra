# BUG BLOQUANT — `mode: upsert` sur PostgreSQL ne fonctionne pas en 0.11.3

> Trouvé le 17/10/2026 en testant pour de vrai le brouillon de réponse à `minimdm#74`.
> Reproduit sur PostgreSQL 16.15, `hydra-etl` 0.11.3 installé depuis PyPI, Python 3.13.

## Symptôme

Tout job PostgreSQL → PostgreSQL en `mode: upsert` échoue, **quelle que soit la table cible**,
même avec une PRIMARY KEY exactement sur les colonnes de `key` :

```
ValueError: PostgreSQLConnector [warehouse]: échec chargement.
  Table : public.product
  Mode  : upsert
  Erreur : KeyError: 0
```

`hdrctl validate .` répond `✅ DSL valid` : le défaut est invisible à la validation, il n'apparaît
qu'à l'exécution. `mode: append` et `mode: replace` ne sont pas touchés.

## Cause — deux défauts cumulés dans `_validate_upsert_key()`

Fichier : `hydra_etl/internal/connector/postgresql_connector.py`, vers la ligne 807.

**1. `array_agg` sur une colonne `sql_identifier` revient en chaîne, pas en liste.**
`information_schema.key_column_usage.column_name` est de type `sql_identifier` ; psycopg2 ne sait
pas décoder un tableau de ce type et retombe sur la représentation texte brute :

```python
{'constraint_name': 'product_pkey', 'constraint_cols': '{record_id}'}   # une str, pas ['record_id']
```

Donc `set(constraint_cols)` est un ensemble de **caractères** et ne peut jamais égaler `{'record_id'}` :
la contrainte valide n'est jamais reconnue. Correctif : `array_agg(kcu.column_name::text ...)`.

**2. Déballage d'une ligne `RealDictCursor` comme si c'était un tuple.**
Le curseur est créé avec `cursor_factory=psycopg2.extras.RealDictCursor` (ligne 149), donc chaque
ligne est un dict :

```python
constraint_name, constraint_cols = constraint    # -> récupère les CLÉS : 'constraint_name', 'constraint_cols'
```

Puis le message d'erreur fait `c[0]` sur ce dict → `KeyError: 0`, qui masque complètement le vrai
diagnostic. C'est pour ça que l'utilisateur voit `KeyError: 0` au lieu de « aucune contrainte ».

Le commentaire du code annonce « CORRECTION BUG 1 : Parsing correct des constraint_cols » — la
correction n'a jamais marché, et aucun test ne couvre ce chemin (sinon il serait rouge).

## Correctif

`ressources/patchs/0.11.3-upsert-postgres.patch` — 3 lignes modifiées, aucun changement d'API.

## Vérification après correctif (mesurée, pas supposée)

Source : `nordkraft.product`, 5 fiches (2 actives, 1 draft, 1 retired, 1 soft-deleted).
Destination : `public.product`, PRIMARY KEY sur `record_id`.

| Passe | Attendu | Observé |
|---|---|---|
| 1 — table vide | 2 lignes chargées | `Rows read 2 / written 2` → 2 lignes |
| 2 — même fenêtre, rejouée | aucun doublon | `written 2` → **toujours 2 lignes** ✅ idempotent |
| 3 — après `UPDATE` d'une fiche en amont | la valeur se propage | `A-1` passe à `Rotor 40 MkII / 131.00` ✅ |

Le filtre `_state = 'active' AND _deleted_at IS NULL` écarte bien draft, retired et soft-deleted :
2 fiches sur 5.

## Autres constats du même test (à répercuter dans la doc et le README)

- **`pip install hydra-etl` n'installe pas le driver PostgreSQL.** Premier échec rencontré :
  `driver manquant. Installez 'psycopg2-binary'`. La bonne commande est
  `pip install "hydra-etl[postgres]"` — les extras existent (`postgres`, `mysql`, `duckdb`,
  `mongodb`, `http`, `mcp`, `native`, `server`, `all`) mais le message d'erreur renvoie vers
  `psycopg2-binary` au lieu de l'extra. **Toute communication qui montre un job PostgreSQL doit
  écrire l'extra**, sinon le lecteur échoue à la première commande.
- **`SELECT *` depuis une source dont le schéma diffère de la cible casse le chargement** :
  `UndefinedColumn: column "_state" of relation "product" does not exist`. Le connecteur insère
  les colonnes du premier batch telles quelles. Toujours lister les colonnes explicitement dans
  `extract.query` (ou passer par `transformations.yaml`).
- **Ce qui marche comme annoncé** : `.env` du dossier job chargé automatiquement ;
  `${ENV:VAR}` substitué y compris **à l'intérieur** de la chaîne SQL de `extract.query` ;
  `extract.query` accepté en place de `extract.table` ; `hdrctl validate [PATH]` et
  `hdrctl run [PATH]` avec le dossier courant par défaut.

## Complément du 17/10 — pourquoi la CI est verte, et état du dépôt

**Cause racine du « bug livré » :** le chemin EST couvert par des tests
(`tests/test_e2e_postgresql.py` : `test_load_upsert_simple_key`, `test_load_upsert_composite_key`),
mais le module entier est désactivé :

```python
pytestmark = pytest.mark.skip(reason="E2E: requires live PostgreSQL containers")
```

Ces tests attrapent de plus leurs exceptions dans `print(...)` + `sys.exit(1)` au lieu d'assertions,
donc même réactivés ils seraient difficiles à lire en CI. **Le correctif seul ne suffit pas : sans
test qui tourne, le bug peut revenir.**
